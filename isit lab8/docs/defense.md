# Ответы на контрольные вопросы

1. **База данных и JSON.** PostgreSQL централизованно проверяет ограничения и связи, поддерживает транзакции, параллельную работу и индексы. В ЛР7 эти задачи приходилось решать кодом и блокировками файлов.
2. **PK и FK.** PK однозначно определяет строку, например tickets.id. FK ссылается на существующую строку, например tickets.category_id → categories.id.
3. **Связи.** 1:N — внешний ключ в дочерней таблице; 1:1 — внешний ключ одновременно является PK или UNIQUE; N:M — отдельная таблица с двумя FK.
4. **Связующая таблица.** ticket_tags хранит отдельные пары заявка–тег. Составной PK (ticket_id, tag_id) запрещает повторную привязку одного тега к одной заявке.
5. **Один к одному.** staff_profiles.staff_id — и PK, и FK на staff. У сотрудника может быть не более одного профиля, тогда как FK без уникальности допускает много дочерних строк.
6. **Ограничения.** PRIMARY KEY обеспечивает идентичность, FK — существование связей, NOT NULL — обязательные поля, UNIQUE — уникальные email/названия, CHECK — длину и допустимые значения, DEFAULT — начальные статус/приоритет/время.
7. **Удаление.** RESTRICT запрещает удалять используемую категорию или автора комментария; CASCADE удаляет комментарии и связи вместе с заявкой, профиль вместе с сотрудником; SET NULL снимает исполнителя, сохраняя заявку.
8. **Нормализация.** ФИО сотрудника не копируется в каждую заявку: хранится только assignee_id. Названия тегов не записываются списком через запятую, а вынесены в tags и ticket_tags.
9. **CRUD и HTTP.** POST — INSERT, GET — SELECT, PUT/PATCH — UPDATE, DELETE — DELETE. В SQL требуется WHERE и контроль связей; преобразование ошибок БД в HTTP будет задачей следующего этапа.
10. **JOIN и LEFT JOIN.** JOIN оставляет строки с парой, LEFT JOIN сохраняет все строки слева. Заявки без исполнителя должны оставаться в результате, поэтому для staff нужен LEFT JOIN.
11. **NULL.** Это неизвестное или отсутствующее значение, обычное сравнение с ним не возвращает TRUE. Используются IS NULL и IS NOT NULL.
12. **Индекс.** Это отдельная структура для поиска и упорядочения. PostgreSQL создаёт индексы для PK/UNIQUE, а индексы на ссылающихся FK и условиях запросов выбирает разработчик с учётом нагрузки: индекс нужен не каждому запросу.
13. **EXPLAIN ANALYZE.** Показывает выбранный план, фактические строки, циклы и время выполнения. Seq Scan читает таблицу последовательно; Index Scan ищет по индексу; Bitmap Scan сначала получает набор адресов, затем читает подходящие страницы. BUFFERS показывает обращения к страницам и кэшу.
14. **Почему индекс не используется.** Таблица мала, условие выбирает большую часть строк, поиск начинается с %, статистика устарела или не подходят ведущие столбцы составного индекса. В работе ILIKE '%...%' и выборка всех статусов сохранили Seq Scan.
15. **Цена индексов.** Индексы занимают диск и кэш, требуют обновления при INSERT/UPDATE/DELETE. Польза проверяется на реальных запросах; уменьшение времени из-за прогрева кэша само по себе не доказывает эффективность индекса.

Для защиты также важно объяснить пропуски SERIAL после откатов: последовательности не откатываются. Поэтому в CRUD используется RETURNING и переменные psql, а не предположение о следующем номере.
