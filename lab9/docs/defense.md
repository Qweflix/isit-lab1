# Контрольные вопросы

1. **Контракт клиента и сервера** — адреса, методы, поля, типы и формат ошибок. Найденные расхождения: tasks/tickets, pending/new, строковый ID/числовой category_id, пустой срок/null.
2. **fetch и ошибки HTTP.** Ответ 404 или 422 не отклоняет Promise автоматически. Проверяется response.ok; сетевая ошибка возникает в catch без HTTP-статуса.
3. **Аутентификация и авторизация.** Вход устанавливает личность; роль определяет права. Неверный токен — 401, запрет удаления оператору — 403.
4. **SQL-инъекция.** Нельзя соединять ввод со строкой SQL. Значения передаются параметрами PDO. Имена столбцов параметрами не передаются, поэтому sort выбирается из белого списка.
5. **Путь запроса.** Router → контроллер → PgRepository → Database/PDO → PostgreSQL → JSON. По сравнению с ЛР7 файловое хранилище заменено подготовленными SQL-запросами.
6. **Хранение пароля.** password_hash создаёт односторонний хеш с солью; password_verify проверяет ввод. Открытый пароль не хранится.
7. **Одинаковое сообщение входа.** Ответ не раскрывает, зарегистрирована ли указанная почта.
8. **Токен.** random_bytes даёт криптографическую случайность. Срок уменьшает время использования украденного токена. В БД хранится SHA-256, чтобы утечка таблицы не давала готовых действующих токенов.
9. **Передача токена.** Клиент ставит Authorization: Bearer в каждом защищённом запросе. Без заголовка сервер возвращает 401.
10. **localStorage.** Токен остаётся после обновления страницы и доступен JavaScript этого origin. Секретные данные и хеши паролей туда не записываются.
11. **Скрытие кнопки.** Запрос можно отправить вручную. Сервер всегда самостоятельно проверяет роль.
12. **401, 403 и 422.** При 401 очищается токен и показан вход; при 403 — недостаток прав; при 422 — ошибки у полей формы.
13. **CORS.** Браузер ограничивает чтение другого origin. Здесь страница и API имеют один origin, разрешение CORS не требуется.
14. **Отзыв при выходе.** Одного удаления в браузере недостаточно: копия токена остаётся действительной. POST logout удаляет его хеш из базы.
15. **Позитивные и негативные тесты.** Создание корректной заявки — 201; короткая тема или неверная дата — 422. Оператор читает заявки — 200, удаляет — 403.
16. **DevTools.** Headers показывает адрес, метод и код; Payload — отправленные поля и типы; Response — JSON ошибки, включая errors при 422.
17. **Уровни тестирования.** API проверяется прямыми HTTP-запросами, сквозные сценарии — Chromium, хранение хешей — запросами к реальной БД. В совокупности они проверяют контракт, интерфейс и безопасность хранения.
