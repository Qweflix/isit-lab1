# Лабораторная работа №9. Интеграция компонентов веб-приложения

## 1. Цель работы

Объединить клиентскую и серверную части системы учёта заявок пользователей, подключить PostgreSQL, реализовать вход и разграничение прав, проверить полный пользовательский сценарий.

Предметная область — **«Система учёта заявок пользователей»**, вариант 6. Работа продолжает ЛР5 (таблица и Fetch API), ЛР7 (PHP REST API, Router, контроллеры) и ЛР8 (реляционная модель PostgreSQL). Исходники изучены в ветках `isit-7` и `isit-8`; предыдущие лабораторные не изменены. Новая работа находится в ветке `isit-9`, папке `lab9`, как в образце оформления.

## 3. Интеграция клиента, сервера и базы данных

Клиент отправляет запрос Fetch на PHP API того же сервера. Единая точка входа проверяет Bearer-токен, Router выбирает контроллер, PgRepository выполняет подготовленный SQL через PDO. PostgreSQL обеспечивает связи и ограничения. Ответ возвращается в JSON, клиент обновляет таблицу без перезагрузки страницы.

Из ЛР5 сохранены простой табличный интерфейс, карточки, оформление CSS, поиск, состояния загрузки/пустого списка/ошибки и безопасный вывод через textContent. Демонстрационные задачи заменены заявками из ЛР7/ЛР8; mock-api.js не подключается. Клиент теперь сохраняет каждое изменение на сервере.

Из ЛР7 сохранены автозагрузка App, Router, контроллеры ресурсов, маршруты и формат ошибок. Общие CRUD-операции вынесены в ResourceApiController и PgRepository. JSON-файлы не используются. Все семь таблиц ЛР8 сохранены: staff, staff_profiles, categories, tickets, comments, tags, ticket_tags. Сохранены их поля, ключи и правила удаления; добавлены users и auth_tokens. Начальные данные — те же шесть заявок, три категории, три сотрудника, комментарии и теги.

## 4. Авторизация и права

Вход выполняется по электронной почте и паролю. В базе хранится password_hash, проверка — password_verify. Случайный токен действует два часа; сервер сохраняет только SHA-256 и срок. При выходе токен отзывается в базе. Хеш пароля клиенту не отправляется.

| Действие | Руководитель (manager) | Оператор (operator) |
| --- | --- | --- |
| Просмотр ресурсов | Да | Да |
| Создание и изменение заявок | Да | Да |
| Удаление заявок | Да | Нет, 403 |
| Изменение справочников через API | Да | Нет, 403 |

Кнопка удаления скрыта у оператора. Сервер проверяет роль независимо от интерфейса. Нет токена или он истёк — 401 и возврат к форме входа. Должность staff.role из ЛР8 сохранена отдельно от роли учётной записи.

Токен хранится в localStorage; содержимое заявок выводится через textContent. Для реальной эксплуатации нужны HTTPS, ограничение попыток входа и дополнительная защита браузерного хранения. В данной учебной версии HTTPS, cookie/CSRF и ограничение входов не реализованы; БД не публикует порт наружу, веб-сервер привязан к loopback.

## 5. Согласование контракта

| Расхождение | Принятое решение |
| --- | --- |
| ЛР5 использовала /api/tasks и mock-данные | Клиент вызывает настоящий /api/tickets |
| Статус pending и учебные приоритеты | Статусы new/in_progress/done и четыре приоритета ЛР7/ЛР8 |
| В ЛР5 не было категории и описания | Обязательные category_id и description добавлены в форму |
| Значение select приходит строкой | category_id и assignee_id преобразуются в числа |
| Пустой срок или исполнитель | Отправляется null, поле срока называется due_date |
| Клиент не проверял HTTP-ошибки | api.js проверяет response.ok; errors показываются у полей |
| Поиск и сортировка могли не совпадать | q/status/category_id, sort/order; столбцы SQL только из белого списка |
| Локальные изменения DOM терялись | POST/PATCH/DELETE сохраняют данные в PostgreSQL |

## 6. Полный пользовательский сценарий

### 6.1. Вход

Пользователь вводит email и локально заданный пароль. При неверном вводе сервер возвращает 401 с одинаковым сообщением для неверной почты и пароля.

![Форма входа](images/01-login.png)
![Ошибка входа](images/02-login-error.png)

### 6.2. Просмотр, поиск и создание

После входа руководителя загружаются заявки и справочники из БД. Поиск работает по теме без учёта регистра; статус и сортировка меняют серверную выборку. Новая заявка сохраняется POST-запросом, после чего список обновляется.

![Список руководителя](images/03-list-manager.png)
![Созданная заявка](images/04-created.png)

### 6.3. Изменение, удаление и проверка полей

«Изменить» заполняет форму существующей записью; «Сохранить» отправляет PATCH. «Решена» меняет статус на сервере, «Вернуть» переводит в работу. Руководитель может удалить запись после подтверждения. При неверных данных сервер отвечает 422, ошибки показаны рядом с полями.

![Ошибки полей](images/05-error-422.png)

### 6.4. Роли и выход

После выхода снова показана форма входа. Оператор видит заявки, но не видит удаление. Прямой запрос DELETE от оператора также запрещён — 403.

![Список оператора](images/06-list-operator.png)
![Ответ 403, сохранённый протокол](images/07-error-403.png)

### 6.5. Истечение сессии и недоступность компонентов

Истёкший токен вызывает 401; клиент очищает localStorage и предлагает войти снова. При пропаже сети или остановке PHP показано «Нет связи с сервером», при остановке PostgreSQL — «База данных недоступна» (503). После восстановления компонента кнопка «Обновить» снова получает данные.

## 8. Найденные проблемы и домашняя доработка

При остановке БД драйвер PDO вернул код 7; первоначально сервер отвечал 500. Ошибка подключения выделена отдельно и возвращает 503, сценарий повторно прошёл. Исправлена команда восстановления контейнера для доступной версии Compose.

В API-тесты добавлены проверки совместных фильтров, сортировки, неверного календарного дня, защиты ID и отозванного токена. Дополнительная возможность из методички — ошибки UNIQUE и FOREIGN KEY преобразуются из SQLSTATE 23505/23503 в 409. Проверены дубликаты категорий/сотрудников и удаление записей с зависимостями.

## 9. Запуск из чистого клона

Нужны Git, Docker Engine и Docker Compose v2. Приложение не требует Composer, npm или Python. Команды для bash:

```bash
git clone --branch isit-9 https://github.com/Qweflix/isit-lab1.git
cd isit-lab1/lab9/src
cp .env.example .env
# В .env заменить DB_PASSWORD своим локальным паролем БД.
docker compose -p lab9 up -d --build --wait
read -r -s -p 'Учебный пароль пользователей (от 8 символов): ' DEMO_PASSWORD
printf '\n'
export DEMO_PASSWORD
docker compose -p lab9 exec -T -e DEMO_PASSWORD web php84 bin/reset-db.php --confirm
```

Открыть **http://127.0.0.1:8000/client/**. Учётные записи `manager@example.test` и `operator@example.test` используют заданный DEMO_PASSWORD. Это учебные адреса; реальные пароли не включены в репозиторий. Команда reset-db удаляет и создаёт таблицы выбранной учебной БД; не применять к рабочей базе.

Если порт занят, изменить APP_PORT в .env и открыть соответствующий порт. Данные сохраняются в именованном томе Compose. Остановка — `docker compose -p lab9 down` (из src). Для браузерных тестов имя проекта по умолчанию lab9.

В облачной среде со своим HTTPS-прокси сборке может потребоваться доверенный CA:

```bash
docker build --secret id=proxy_ca,src=/etc/ssl/certs/ca-certificates.crt -t lab9-web .
docker compose -p lab9 up -d --no-build --wait
```

Без Docker нужны PHP 8.2+ с pdo_pgsql и mbstring и отдельная PostgreSQL 16+. Задать DB_HOST, DB_PORT, DB_NAME, DB_USER, DB_PASSWORD и DEMO_PASSWORD в окружении; выполнить `php bin/reset-db.php --confirm`, затем `php -S 127.0.0.1:8000 -t public public/index.php`. Проверенный вариант этой работы — Docker.
