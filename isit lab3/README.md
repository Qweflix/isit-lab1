**Модуль:** Архитектура современных информационных систем  
**Тема:** Архитектура веб-систем: клиент, сервер и API  

---

## 1. Цель работы
Изучить принципы проектирования архитектуры информационных систем, определить структуру приложения, спроектировать взаимодействие между основными компонентами и подготовить структуру программного проекта для дальнейшей разработки.

---

## 2. Архитектурный стиль
В качестве архитектурного стиля выбрана **трёхуровневая архитектура**.

**Уровни архитектуры:**
1.  **Frontend (Клиентская часть):** Веб-интерфейс, с которым взаимодействует пользователь. Отвечает за отображение данных и отправку запросов.
2.  **Backend (Серверная часть):** Обрабатывает бизнес-логику, принимает запросы от клиента, взаимодействует с базой данных и внешними сервисами.
3.  **Database (База данных):** Обеспечивает постоянное хранение и целостность данных.

**Преимущества выбора:**
*   **Разделение ответственности:** Каждый уровень занимается только своей задачей.
*   **Масштабируемость:** Можно масштабировать Backend независимо от Frontend.
*   **Независимость разработки:** Фронтенд и бэкенд могут разрабатываться параллельно.

---

## 3. Компоненты системы

Основные компоненты серверной части (Backend) и их ответственность:

| Компонент | Назначение |
| :--- | :--- |
| **Controllers** | Принимают HTTP-запросы, валидируют входные данные, вызывают сервисы и возвращают JSON-ответ. |
| **Services** | Содержат основную бизнес-логику |
| **Repositories** | Отвечают за взаимодействие с базой данных |
| **Models** | Описывают структуру сущностей предметной области |
| **Routes** | Определяют маршруты API |

---

## 4. Взаимодействие компонентов

Взаимодействие строится по принципу **Request-Response** через REST API:
1.  **Пользователь** выполняет действие в интерфейсе 
2.  **Frontend** формирует HTTP-запрос и отправляет его на **Backend**
3.  **Controller** принимает запрос и передает управление в **Service**
4.  **Service** выполняет бизнес-логику и через **Repository** сохраняет данные в **Database**
5.  Результат возвращается по цепочке обратно пользователю

---

## 5. Индивидуальная особенность предметной области

**Особенность:** Интеграция с внешним сервисом для отправки уведомлений о статусе заказа.

**Описание:**
В отличие от типовых CRUD-операций, при смене статуса заказа система должна инициировать отправку письма пользователю. Это требует взаимодействия с внешним API

**Ответственный компонент:**
За эту логику отвечает отдельный **NotificationService** (Модуль уведомлений), который вызывается внутри основного сервиса заказов. Это позволяет не блокировать основной процесс оформления заказа, если внешний сервис отвечает долго (асинхронная обработка).

## 6. Структура проекта

Структура каталогов отражает разделение на уровни и компоненты:

```text
project/
├── frontend/             # Клиентская часть (HTML/CSS/JS или React/Vue)
├── backend/              # Серверная часть (PHP/Node.js/Python)
│   ├── controllers/      # Обработчики запросов
│   ├── services/         # Бизнес-логика (включая NotificationService)
│   ├── repositories/     # Работа с БД
│   ├── models/           # Модели данных
│   └── routes/           # Маршруты API
├── database/             # SQL-скрипты и миграции
├── docs/                 # Документация
